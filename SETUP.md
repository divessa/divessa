# DIVERSA — deployment and maintenance

This guide is for the profile repository **`divessa/divessa`**. All visible profile copy in `README.md` is in English and remains accurate even before a visualization has been generated. **No GitHub credentials or personal access token are required.** The package has not been published to your account.

## 1. Upload to the existing profile repository

Upload or commit the `README.md`, `.gitignore`, and all three `.github/workflows/*.yml` files from this package into the **root** of `https://github.com/divessa/divessa` on its default branch. Keep the folder structure intact. This README will replace the current profile README *only when you choose to commit it*. Keep a copy of the old README if you might want to restore it.

The files below `assets/`, `koi/`, and `profile-3d-contrib/` are generated by the workflows. They are intentionally absent from the ZIP until GitHub generates **real account data**. The README image references are valid target paths but will display missing-image placeholders before the first successful workflows. Do not create synthetic fish data or copy somebody else's generated GIF.

## 2. Enable Actions and run the generators

1. Ensure GitHub Actions is enabled for `divessa/divessa`, including use of third-party actions.
2. In **Settings → Actions → General → Workflow permissions**, select **Read and write permissions** for `GITHUB_TOKEN` (where this choice is available). The workflows also request job-level `contents: write` and no broader access.
3. From the repository's **Actions** tab, run **DIVERSA | Living Koi**, **DIVERSA | Repository Intelligence**, then **DIVERSA | Contribution Terrain** with **Run workflow** on the default branch.
4. Verify that the workflows commit the generated assets to the profile repository and that the README displays them. Refresh GitHub if image caching delays a change.
5. If an action cannot push because of branch protection, use an appropriately authorized deployment strategy or adjust the repository's rules; do not weaken protections casually.

The GitHub-generated token is passed to the third-party actions via `${{ secrets.GITHUB_TOKEN }}`. No manual secret creation is needed for the public-data configuration in this package. The read/write workflow permissions apply only to the profile repo, not to project code repositories.

The koi is an **animated GIF** generated from real public GitHub history. The original `git-koi` project fixes the image's native pixel dimensions and recommends displaying its GIF at `width="256"`. Its `asagi` body is a supported style, not a custom creature or renderer.

The profile-cards action is configured with `commit: false`; a single minimal shell commit step stages its output and the pin-card output together. This avoids multiple concurrent writes from one workflow. Optional pin-card failures are nonfatal so previously committed graphics remain in place. Other generation jobs are independently scheduled at different times.

**Manual dispatch** is available for all three workflows. They also run when their own workflow YAML changes. Unchanged artifacts are not committed.

**Important:** GitHub may automatically disable scheduled workflows in public repositories after 60 days of inactivity. Re-enable them in the Actions tab and manually run them if necessary.

## 4. Confirm the koi is real and animated

- Open `https://github.com/divessa/divessa/blob/main/koi/koi.gif` after a successful **DIVERSA | Living Koi** run.
- Confirm the actual `koi.gif` file exists, is not a placeholder, and animates when viewed.
- Confirm the profile README embeds the same repository-local `./koi/koi.gif` path. It is not a snake; it comes from `yalongwastaken/git-koi`.
- Inspect the Action log for GitHub activity collection and GIF rendering. A completed GIF also updates only when its underlying deterministic rendering changes.

## 5. How the project links and contribution funnel work

The showcase currently includes exactly two explicitly verified technical repositories:

- `https://github.com/divessa/Historical_Drift_Analyzer` — an evaluated, modular temporal-RAG research prototype.
- `https://github.com/divessa/bibcleaner-pro` — a dependency-light BibTeX deduplication utility.

The README links to real repository **Issues** and **Pull requests** tabs. It does **not** claim that `good first issue` labels, discussions, contribution guides, community members, funded products, or active commercial offerings exist. To improve onboarding later, add issue templates, `good first issue`/`help wanted` labels, `CONTRIBUTING.md`, a license where appropriate, and Discussions **in each business repository itself**. Those repositories are not modified by this ZIP.

**New project later:** add another verified project subsection in `README.md` and a `pin` step in `repository-intelligence.yml` if you want another generated project card. Keep the profile project-first; do not automatically add an empty card for every project. If the owner username changes, update the static repo links and `options: username=...` strings in the stats action. The other generators use `${{ github.repository_owner }}` automatically.

## 6. Runtime limits and reliability

- GitHub does not execute arbitrary JS, Canvas, or WebGL from profile READMEs. All motion is contained in GIF or generated SVG; the graphics are not interactive applications.
- Hosted `capsule-render` and `readme-typing-svg` images depend on their respective public services. The repository headings, project descriptions, navigation, and links work independently of those services.
- This offline package contains **real workflow definitions**, but the current environment could not call GitHub Actions or download the true account-specific GIF. The generated artifacts must be runtime-verified on your actual account after you run the workflows.
- All third-party action versions are fixed to observed release tags. For stronger supply-chain pinning you can replace tags with verified full commit SHAs after reviewing your security requirements.
- Daily scheduled refreshes can encounter GitHub API limits or Git push conflicts. Old successfully committed assets remain available. Re-run any failed workflow after resolving the issue.
- Repository statistics and contribution heatmaps are not measures of users, growth, revenue, product quality, or commercial viability.

## 8. Why other investigated generators were omitted

- `lowlighter/metrics`: broad functionality, but many relevant advanced views require an additional scoped token and overlap the repository-oriented cards selected here.
- `GermanAndresLopez/terminal-readme-github-stats`: excellent repository-terminal rendering, but the documented deployment is local CLI or self-hosted Vercel, not a directly hosted maintenance-free image endpoint. Embedding a guessed demo domain would risk a broken profile. The selected typing SVG provides a restrained command-line feel without a new service deployment.
- `navi3582/animated-github-profile`: its ASCII portrait is personal-identity-centric; copying supporting scripts also adds maintenance for little repository value.
- `Platane/snk`: a second contribution creature would compete with the mandatory koi.
- `vn7n24fzkq/github-profile-summary-cards`, `Ashutosh00710/github-readme-activity-graph`, and full `stats-organization/github-stats-extended` account-summary cards: largely duplicate information and push the profile toward personal vanity metrics. The selected Stats Extended **repository pin card Action** is used instead.
- `honzaap/GithubCity`: WebGL cannot execute in a GitHub README and a nonfunctional embedded version would mislead visitors.

The chosen combination deliberately prioritizes **two real repositories, a useful contribution path, then living imagery and telemetry**.
